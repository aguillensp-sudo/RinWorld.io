# F-217

- **Fecha:** 2026-09-26
- **Origen:** Al diseñar el alta de `FRU` (Registro de usuario adicional)
- **Clasificación:** `SPEC-GAP`
- **Capability:** organization-onboarding

## Síntoma

**El alta de un usuario adicional crea una cuenta que nadie puede completar.** El HTML aprobado de `FRU` dice que la contraseña *«la establecerá ahora el administrador»*, así que hace falta crear la cuenta de Auth desde el servidor (`register-additional-member`, service key). Pero el nuevo usuario queda `REGISTERED` y el flujo que lo llevaría a `ACTIVE` (su propia frase de seguridad: `REG-05`, `REG-06`, `REG-07`) no existe. Además: no hay correo (no hay proveedor), así que el ADMIN tiene que pasarle las credenciales por su cuenta; y la cuenta se crea con el correo ya confirmado.

## Acción en V1

Construido tal cual dice el HTML, con el mínimo de superficie: función de borde que valida el JWT y el rol del que llama, repite la validación del formulario y borra la cuenta de Auth si falla la fila de `members`; `add_registered_member` (0038) solo la ejecuta `service_role` y aplica el límite de 5. Un `REGISTERED` no pasa `app.is_active_member()` y no escribe nada, **pero SÍ lee datos de su organización: la afirmación original de que no leía era falsa (`F-222`).**

## Estado

**CERRADO el 7-oct-2026.** `ACT-02` lleva a un EDITOR `REGISTERED` por `REG-05`→`REG-07`; con `0050` se activa solo y puede empezar con una clave nueva. El alta de `FRU` se mantiene, con la variante de contraseña provisional (`F-241`).
